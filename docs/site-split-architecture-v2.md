# 모멘텀마케팅 사이트 분리 / 중복개발 방지 기준서 v2.0

- 작성일: 2026-10-19
- 기준 저장소: `goldeye24-hub/momentum`
- 상태: **설계안 / 코드 및 운영 배포 전**
- 목적: 마케팅 고객유치 사이트와 웹에이전시 포트폴리오 사이트는 독립 운영하되 순위 엔진, API, 회원, CRM, 원본 데이터는 중복 개발·중복 보관하지 않는다.
- **기능의 실제 작동·장애·테스트 수준은 [기존 QA 기준](./service-map-and-qa.md)을 우선한다.** 이 문서는 두 사이트의 *역할과 소유권, 분리 순서*의 단일 기준이다.

## 1. 확정 원칙

1. **2개 공개 사이트 + 1개 공통 서비스/관리자 + 1개 기존 DB를 기본안으로 한다.** 두 번째 공개 사이트의 백엔드, 회원, DB를 새로 만들지 않는다.
2. 기존 `momentum` GitHub/Vercel, `/lab/`, `/lab/rank/`, `/platform/`, `/admin/`, `/admin/studio/`, `api/place-rank-live.js`, `api/_place-observe.js`, `api/_rank-store.js`, 순위 기록 테이블은 삭제하지 않는다.
3. 플레이스 순위 수집은 **기존 엔진 한 벌**만 사용한다. 마케팅 공개 조회와 내부 대시보드는 각자 별도 수집기를 만들지 않는다. 동일 조건 캐시, 요청 제한, 실패 상태를 공유한다.
4. 공개 마케팅 콘텐츠는 기존 `momentum`에, 제작 서비스 소개·포트폴리오의 *최종 원본*은 신규 `momentum-web`에 둔다. 이전 중에는 원본 소유 위치가 한 곳인지 확인한다.
5. 두 공개 사이트는 디자인과 SEO 목적을 분리하고 상호 링크한다. 회원/관리자 로그인은 마케팅의 기존 서비스에서만 시작한다.
6. 고객 문의와 제작 견적은 **공통 리드/CRM 모델**로 합치되, 현재 CRM은 브라우저 로컬 저장 중심으로 서버 저장이 미구현이다. 중앙 서버 API의 운영 검증 전에는 두 사이트의 데이터가 통합됐다고 주장하지 않는다.
7. 실제 구현 전 '기존·정상 / 기존·오류 / 코드만 있음 / 신규 필요 / 외부 연동 검증 필요'로 분류한다. 이미 존재하는 기능을 재제작하는 작업을 금지한다.
8. 마케팅 홈페이지의 지식iN 관련 상위노출·배포 서비스 문구는 모든 공개 화면·SEO 메타데이터에서 제외한다.
9. 본 설계 문서를 승인/병합하기 전에는 운영 URL, DNS, DB, 기존 SEO 리디렉션, 인증 설정을 변경하지 않는다.
10. 운영 완료 판정은 **코드 작성 → 테스트 통과 → 배포 일치 → 운영 실측/E2E 확인**이다. 중간 상태는 완료로 표현하지 않는다.

## 2. 사이트와 기능의 유일 소유권

| 구분 | 공개 마케팅 사이트 (기존 momentum) | 웹에이전시 사이트 (신규 momentum-web) | 공통 백엔드·관리자 (기존 momentum) |
| --- | --- | --- | --- |
| 핵심 역할 | 소상공인/지역사업자 유입 → 조회 → 마케팅 상담 | 디자인·실적 증명 → 제작 문의/견적 | 고객·데이터·운영/수주/분석 |
| 공개 상품 | 플레이스·블로그·바이럴·광고·로컬SEO 대행 | 홈페이지·랜딩페이지·상세페이지 제작 | 없음(운영 전용) |
| 무료 조회 | 키워드 조회, 플레이스 순위, 시즌별 키워드, 상권 기초 조회 | 직접 구현 금지: 마케팅 도구에 링크 | 키워드 공급자 연동, 순위 측정, 상권 데이터 어댑터 |
| 포트폴리오 | 제작 사례 티저 + 웹에이전시 연결 | **최종 정본**(샘플/실제 실적 명확히 구분) | 포트폴리오 메타데이터 저장은 추후 필요할 때만 |
| 견적·상담 | 마케팅 상담 진입 | 제작 견적 진입 | 공통 lead/quote 기록, source_site 값으로 분리 |
| 회원 | 기존 `/platform/` 링크 | 별도 회원가입·로그인 구현하지 않음 | 기존 회원/관리자 인증만 활용 |
| 내부 분석 | 운영 메뉴 표시하지 않음 | 운영 메뉴 표시하지 않음 | 기존 `/admin/` 기능 복구 후 확장 |
| DB | 비밀키·관리자 직접 접근 금지 | 비밀키·관리자 직접 접근 금지 | 기존 momentum-marketing Supabase를 권위 저장소로 유지 |

예상 접속 예: `기존 마케팅 도메인/` ↔ `studio.기존마케팅도메인/`. **도메인은 미확정**. 실제 DNS/배포 주소는 이후 결정한다. 공통 API/관리자를 웹에이전시 도메인으로 복제하지 않는다.

### 기존 라우트에서 분리 후 라우트로

| 기존 위치 | 조치 | 조건 |
| --- | --- | --- |
| `/`, `/services/*` | 유지(마케팅 메시지로 개편) | 기존 상담/분석 링크 회귀검사 |
| `/lab/`, `/lab/rank/`, `/lab/keywords/` | 유지·재사용, 메뉴만 단순화 | 기존 직접접속 및 순위 측정 유지 |
| `/platform/` | 유지 | 기존 세션/DB E2E 검증 |
| `/admin/*` | 유지 | 관리자 API 권한 테스트 |
| `/portfolio/conversion/*`, `/website-samples/*`, `/work/*` 등 | 웹에이전시에 목표별 이전 | 새 도메인 공개 + 자산·SEO 점검 후 구 주소는 매핑별 **301** |
| 웹에이전시 `/`, `/portfolio/`, `/services/`, `/request/` | 신규 제작 | 웹에이전시 전용 UI·SEO |
| 양 사이트의 상담/견적 | 공통 리드 API 사용 목표 | 중앙 API 실구현·검증 전에는 마케팅 사이트의 기존 상담 진입으로 안전하게 연결 |

> **SEO 이전 주의**: 이미 `vercel.json`에 `/website-samples/*` → `/portfolio/conversion/*` 리디렉션이 있다. 무조건 교체하지 않는다. 신규 포트폴리오 공개 검증 후 구 URL별 *최종 URL*을 정하고 1회 리디렉션으로 정리한다. canonical/사이트맵/내부 링크를 함께 갱신하며 '실제 제작 실적'과 '디자인 샘플'을 구분한다.

## 3. 기능 인벤토리: 재사용인가 신규인가

실제 상태 기준은 `docs/service-map-and-qa.md`이며, 아래 '소유권'은 신규 설계다.

| 기능 | 소스/기존 경로 | 지금 아는 상태 | 소유권 및 작업 |
| --- | --- | --- | --- |
| 플레이스 수동 실측 | `api/place-rank-live.js`, `api/_place-observe.js`, `/lab/rank/` | 코드 있음·부분 실측; 429/차단 가능 | **그대로 재사용**; 로직 복제 금지 |
| 순위 기록 DB | `api/_rank-store.js`, 관리자 watch | 코드 있음; 관리자 DB 접근 실패 보고 | **기존 DB 복구 P0** |
| 회원 등록/이력 | `/platform/`, `/api/member-*` | 코드/모의 검증; 실계정 E2E 미검증 | **기존 영역 보존** |
| 정기 순위 측정 | `api/rank-watch-cron.js` | 코드만 있고 스케줄 미활성 | 정책/비용/DB 검증 후 단계적 활성화 |
| 기본 매장 진단 | `/lab/` | 코드/화면 존재; 일부 자체 추론/체크리스트 | 그대로 두고 실측/추정 구분 |

| 내부 CRM | `/admin/crm/` | 브라우저 로컬 저장·서버 저장 미구현 | 기존 자료 백업 → 서버 스키마/이관 → API E2E |
| 웹에이전시 홈페이지 | 신규 | 미구현 | 별도 UI repo, 기존 백엔드 복제 금지 |

## 4. 공통 모듈: 한 번 만들고 다 같이 사용

```text
[marketing-public] --------------------+
  /lab/keyword, /lab/rank, /lab/season  |
  /lab/commerce-area, /contact         |      [momentum server/API]
                                        +---->  place-rank engine (EXISTING)
[web-agency-public] -------------------+       keyword providers (PLANNED)
  /, /services, /portfolio, /request             trade-area providers (PLANNED)
                                                lead/quote service (PLANNED)
  회원/관리자 기능을 절대 복제하지 않음          rank store (EXISTING)
                                                     |
                                            [기존 Supabase DB]
                                                     |
                                      [기존 admin/ 및 platform/]
```

- 플레이스 결과 공통 자료형: `keyword`, `place_id`, `scope`, `status`, `rank`(없으면 null), `observed_at`, `source`, `approximate`, `observed_count`. **기존 API 반환 스키마와 호환을 유지**하고 필요하면 어댑터를 둔다.
- **scope를 섞지 말 것**: 네이버 모바일 목록 / PC 지도 목록 / PC 통합검색 플레이스 블록은 동일 순위가 아니다.
- 키워드 API: 공급자, 관측 시각, PC/모바일 구분, 실제 월간 검색량 vs 상대 추이지수를 명시한다. 공급자 키는 서버에서만 보관한다.
- 상권 API: 조회 지역/기준일/업종 분류/출처를 표시하고 공공데이터 이용 약관·캐시 제한을 확인한다.
- 무료 조회 API: 동일 조건 캐시, 서버 호출량 제한, 실패/미측정 상태 노출, 크론과 예산 상한을 둔다. 차단 회피 자동화나 허위 순위 제공을 하지 않는다.
- 제작 사이트 → 공통 CRM: **초기에는 마케팅 상담 페이지로 출처 태그를 전달**해 중복 DB를 피한다. 추후 웹에이전시 서버의 서버-서버 요청으로 검증된 접수 API를 사용하고 허용된 출처와 검증 토큰·속도 제한을 적용한다. Supabase service role secret을 프런트에 주지 않는다.
- CRM 논리 모델(서버 저장 구현 전 설계): `lead_id`, `source_site`(marketing/agency), `source_page`, `service_type`, `business_name`, `contact_name`, `contact_channel`, `message`, `consent_version`, `created_at`, `pipeline_status`. 개인정보와 마케팅 수신 동의는 구분한다. 기존 데이터 백업 후 **별도 마이그레이션** 검증; 기존 9개 테이블 재작성 금지.
- 중복 문의 방지: 서버 발급 요청 ID로 재시도 중복 방지. 동일 전화번호라는 이유만으로 다른 견적/프로젝트를 합치지 않는다.

## 5. 화면 IA — 사용자에게 보이는 메뉴만 분리

### 마케팅 공개 사이트
- 홈: 한 줄 가치제안, 무료 조회 진입, 핵심 마케팅 상품, 상담.
- 무료 도구: ① 간단 키워드 검색량 ② 플레이스 순위 ③ 시즌별 키워드 ④ 상권·경쟁 점포 개요.
- 서비스: 플레이스·바이럴·블로그·광고대행.
- 고객사례: 마케팅 성과 사례. 웹 제작 사례는 웹에이전시 링크만.
- 마케팅 진단/문의.
- 로그인은 기존 `/platform/`로 연결; `/admin/`은 노출 탐색메뉴에 두지 않는다.

### 웹에이전시 공개 사이트
- 홈: 시각적 레퍼런스와 포트폴리오.
- 서비스: 홈페이지/랜딩페이지/상세페이지.
- 포트폴리오: 실제 제작/디자인 시안 별도 필터 + 업종별 분류.
- 제작 프로세스·FAQ.
- 견적 문의: 필요한 제작 목적, 업종, 참고사이트, 기능, 일정(옵션), 연락처.
- 하단: '마케팅 운영도 필요하신가요?' → 기존 마케팅 사이트 링크.
- 별도 관리자/회원/플레이스 API 없음.

### 공통 관리자(마케팅 도메인에서만)
- 운영 개요.
- CRM: 마케팅 리드와 제작 리드를 `source_site`로 필터링.
- 고객사/계약/견적/프로젝트: 신규 저장이 안정화되면 단계별 구현.
- 플레이스 watch/이력/경쟁사/키워드: 기존 엔진 그대로.
- 콘텐츠/포트폴리오 메타·보고서: 실사용 수요가 확인되면 추가.
- 권한과 로그: 비인가 사용자는 API에서 차단.

## 6. 실행 순서 / 다음 단계 재작업 방지 게이트

| 단계 | 할 일 | 통과해야 할 기준 |
| --- | --- | --- |
| 0. 현황 동결 | 기존 URL, 코드, 테이블, 환경변수 *이름*, SEO, 포트폴리오, 사용자 데이터 목록화 | 기존 기능 소유자/상태를 표기하고 백업 방안 확보 |
| 1. P0 복구 | 순위 DB 오류, 회원 실계정 E2E, 공개/회원/관리자 권한 점검 | 운영 DB 읽기 성공, 수동 측정→저장→조회 일치 |
| 2. 마케팅 구조 정리 | `/` 개편, 무료 조회 4개 메뉴 분리, 기존 경로 유지 | 순위 조회 회귀테스트·조회 실패 상태·문의 정상 확인 |
| 3. 웹에이전시 구축 | 새 repo + 새 Vercel 프로젝트, 재사용 포트폴리오 정리, 디자인·견적 | 브라우저·모바일 QA, 모든 샘플 자산 정상 표시 |
| 4. 두 사이트 연결 | 상호링크, 포트폴리오 SEO 이전, 공통 리드 수집 | 구 URL 301/캐노니컬/사이트맵, 중복 리드 방지 |
| 5. 내부 고도화 | 시즌 키워드·상권 공급자, CRM 서버 저장, 고객보고서, 스케줄 모니터링 | 공급자 정확성·쿼터/비용, 서버 저장·권한 E2E |

**단계 2와 3의 화면 제작은 병행 가능**하지만, 단계 1의 데이터/인증 오류를 복제하거나 우회하여 구현하지 않는다. 새 기능의 외부 API 키 발급과 유료요금 승인은 별도 결정한다.

## 7. 개발/배포 규칙(강제 체크리스트)

작업 카드마다 다음을 기록한다.

```yaml
feature_id: MKT-RANK-001
owner_repo: goldeye24-hub/momentum
owner_module: api/place-rank-live.js
public_surfaces: [/lab/rank/, /platform/, /admin/watches/]
status: code-exists-partial-validation
data_source: naver-browser-observation
requires_new_engine: false
qa: [existing-tests, public-observation, saved-history-consistency]
deployment: not-changed-by-this-blueprint
```

- **작업 전**: 소유 repo/파일·기능 ID 존재 여부 확인 → 동일 기능 발견 시 재사용. 작업 범위/변경 파일과 영향 URL을 먼저 정한다.
- **작업 중**: 사용자 데이터·기존 URL·서비스키 보존. 새 테이블/백엔드 신설 전 기존 DB·API와 중복인지 검사한다.
- **작업 후**: 자동 테스트 + 공개 GET/브라우저 + 실제 인증/실측 + 배포 커밋 대조. 미검증 항목을 따로 기록한다.
- **되돌리기**: 기존 운영 커밋·리디렉션 매핑·데이터 백업을 기준으로 rollback 가능하게 한다.
- **비용 관리**: 동일 API를 사이트별로 따로 호출·결제하지 않도록 요청 캐시·사용량 상한·서버 비용 기록.
- **금지**: 기존 엔진을 재구현, 검증 안 된 수치 노출, 실적 없는 시안을 실적이라 표기, 운영 배포 전에 완료 선언, 기존 DB/로컬 데이터 삭제, 권한 검사 없는 공용 DB 직접 호출.

## 8. 현재 보류된 기술 결정(추측하여 개발하지 않음)

1. 웹에이전시 운영 주소: 서브도메인 vs 별도 신규 도메인. 초기 저비용안은 서브도메인이다.
2. 키워드 실제 검색량·시즌 트렌드 API 공급자 및 키 발급 주체: 공급자/비용/사용 약관 검증 후 결정.
3. 상권정보: 공공 점포정보와 소상공인365 웹 서비스 전체 데이터는 별개이다. 공개 연동 범위 확인 후 확정.
4. 포트폴리오 이전 대상: 기존 `/portfolio/conversion/`의 개별 샘플 URL 및 이미지 자산 전체 목록을 별도 인벤토리로 확정.
5. 통합 CRM: 기존 브라우저 로컬 자료 내보내기 및 신규 저장/접수 API E2E 이후 활성화.
6. 로그인/유료서비스: 웹에이전시는 첫 출시에서 로그인 없이 운영, 마케팅 기존 회원체계는 검증 후 공개한다.

## 9. 이 문서의 변경 통제

- 사이트 역할·소유권·이전 순서를 바꾸면 **이 문서 먼저 수정**한다.
- 기존 기능의 검증 상태/버그/QA 근거는 오직 `docs/service-map-and-qa.md`에서 관리한다.
- 디자인 참고 파일은 별도 자료이며 구현 사실을 증명하지 않는다.
- 본 문서는 신규 프로젝트 설계 기준이다. **작성/병합 자체가 서비스 배포나 통합 DB 연동의 완료를 의미하지 않는다.**
